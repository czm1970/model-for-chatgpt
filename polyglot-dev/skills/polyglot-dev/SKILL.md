# 多语言开发

将用户需求落实为可运行、可验证的代码。解释默认使用用户的语言；代码命名、注释和目录遵循项目已有约定。

## 确定项目和范围

- 先阅读适用的 AGENTS.md、入口、依赖清单、锁文件、构建配置及相关测试，确认实际技术栈。多语言仓库只检查此次改动涉及的组件及其调用边界。
- 已有项目沿用版本、框架、包管理器和测试工具。新项目根据用途选择最小可运行结构；只有语言、运行平台或验收行为缺失且无法推断时才询问。用户列出多种语言不意味着每个项目都要使用全部语言。
- 优先使用仓库提供的 wrapper、脚本及本地工具。缺少 SDK 或编译器时报告具体缺项和受影响检查，不将静态阅读描述为运行成功，也不擅自修改全局开发环境。

## 实现与验证

- 把需求转成可观察的行为，检查输入、输出和失败情形。修复缺陷时先定位触发条件及根因，避免只绕过表面错误。
- 按现有架构完成最小充分改动。跨语言接口明确字段类型、编码、空值、时间格式和错误契约；需要时验证生产方与消费方的兼容性。
- 不为小改动引入框架、全仓格式化或依赖升级。依赖确有必要时沿用现有管理工具并保持清单与锁文件一致。
- 运行与改动有关的构建、测试或页面检查。行为变更优先验证正常路径、关键边界和原始失败场景；纯文案或样式改动采用相称的检查。
- 命令示例仅用于选择检查方法，不能假定工具已安装或直接照搬。检查已有脚本的作用，避免在验证时调用部署、生产数据库或外部收费服务。
- 交付时说明实现结果、运行方式、实际执行的检查及未验证之处。新项目提供必要的启动说明和配置示例，不在示例中写入凭据。
